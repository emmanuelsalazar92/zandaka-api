# Presupuestos mensuales — ZA-97

Implementación del 5 de noviembre de 2026. El nuevo plan mensual conserva el origen USD del ingreso, las asignaciones USD/CRC y el libre sin convertir. Usa `budget_plan`, un almacenamiento auxiliar independiente del presupuesto anterior. **No se ha preparado ninguna base del usuario durante la implementación.** Para entregar el bloque seguir [deploy-testing](deploy-testing.md); publicar imágenes no instala el esquema ni despliega testing.

## Modelo y compatibilidad

Un documento `version: 1` identifica mes presupuestado, mes de cobro, cuentas USD de referencia, modo de ingreso, cotización bancaria, líneas y sobres de fondos por cuenta. Los importes de entrada y resultados de planificación son cadenas decimales. El ingreso base es USD; los pagos pueden ser USD o CRC. No se deduce de nuevo un salario ya neto.

Los estados son `draft` → `finalized` → `funded`. Un preparado puede volver a borrador mientras no esté asignado. Cada escritura incrementa `revision`; una revisión obsoleta devuelve 409. Solo existe un plan por usuario y mes. El ID es un UUID generado antes de guardar, estable durante recuperación. Un borrador admite campos incompletos, pero referencias de cuentas/sobres inválidas se rechazan al guardar. Preparar exige cálculo completo, destinos y fuentes válidos; la disponibilidad se vuelve a comprobar al aplicar.

`budget`, sus líneas, sus contratos `/api/budgets` y las reglas salariales existentes no cambian. La web conserva los presupuestos anteriores en `/budgets/legacy` y sus detalles numéricos. No se convierten ni recalculan documentos históricos. Copiar asignaciones busca el plan nuevo inmediatamente anterior, genera IDs de línea nuevos y conserva ingreso/cotización del actual; requiere guardar explícitamente después.

## Cálculo reproducible

`src/utils/budget-plan.ts`, reflejado en la web, usa Decimal con 60 dígitos de precisión. No convertir resultados de pantalla nuevamente en entradas.

| Concepto                        | Regla                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ingreso neto                    | Entrada directa o bruto − CCSS real − renta real del comprobante. En modo comprobantes debe coincidir exactamente con quincena 1 + quincena 2. No se calcula renta con un tipo de cambio supuesto.                                                                                                                                                                                             |
| Compra presupuestaria USD → CRC | `floor(compra bancaria × (1 − margen / 100))`.                                                                                                                                                                                                                                                                                                                                                 |
| Venta presupuestaria CRC → USD  | `ceil(venta bancaria × (1 + margen / 100))`. Fuente y fecha manuales; margen entre 0 y 20 %.                                                                                                                                                                                                                                                                                                   |
| Compromiso fijo CRC             | Pago original CRC; reserva USD = CRC / compra. Si se elige colchón, subir **cada línea** al dólar entero siguiente antes de sumar.                                                                                                                                                                                                                                                             |
| Fijo USD                        | Reserva original USD; pago USD o equivalente CRC a compra. No se sube al dólar entero.                                                                                                                                                                                                                                                                                                         |
| Porcentaje                      | Porcentaje del neto USD; equivalente CRC a compra cuando corresponde. Sin redondeo adicional al dólar; conservar precisión intermedia.                                                                                                                                                                                                                                                         |
| Suscripción                     | Precio **antes de impuesto**, impuesto configurable explícito. Precio USD pagado CRC: sumar impuesto, multiplicar por venta, redondear al múltiplo de CRC 50 más cercano, obtener reserva USD dividiendo por compra y aplicar el colchón elegido. Precio CRC pagado CRC omite la conversión inicial. Un precio que ya incluye impuesto debe ingresarse con impuesto 0 para evitar duplicación. |
| Liquidación                     | Solo el importe que llegará al sobre se liquida a dos decimales, HALF_UP. La explicación conserva el equivalente previo; los porcentajes no se redondean antes de convertir.                                                                                                                                                                                                                   |
| Referencias                     | 50/30/20 del neto; un grupo excedido se muestra, no obliga a gastar sus referencias ni a convertir el 100 %.                                                                                                                                                                                                                                                                                   |
| Libre                           | Neto − reservas USD. Permanece en la cuenta USD seleccionada; no genera asignación automática. Cierre = neto − asignado − libre = 0.                                                                                                                                                                                                                                                           |

La cotización es una hipótesis de planificación, no una orden bancaria ni una cotización API. El impuesto y los rebajos son datos del usuario; no se presentan como tasas legales actualizadas. Los pagos reales, la conversión de divisas y los traslados bancarios deben registrarse mediante los flujos correspondientes antes de distribuir fondos entre sobres. No se ejecuta automáticamente el día 1.

## Aplicación sin crear dinero

El fondeo anterior generaba ajustes positivos y exigía distribuir el 100 %. El nuevo flujo no lo reutiliza: redistribuye **fondos ya existentes** usando `TransferService`, dentro de la misma cuenta y moneda de cada destino. La cuenta bancaria conserva su total. Se requiere un sobre de fondos distinto de todos los destinos por cada cuenta; no se compensa con el saldo de otra cuenta ni con el libre. No admite saldo insuficiente aunque la cuenta permita sobregiro.

Todo el lote se ejecuta en una transacción SQLite inmediata exterior: transferencias balanceadas, sus confirmaciones `transfer_request` y recibo/estado del plan se confirman juntos. Un fallo posterior revierte también las primeras líneas. Al aplicar se vuelven a validar propiedad, actividad, monedas, saldos, estado y revisión. La fecha contable no puede ser anterior al primer día del mes ni posterior a hoy en `America/Costa_Rica`.

La aplicación exige `requestId` UUID, revisión y fecha inmutables. Repetir el mismo intento en un plan ya asignado devuelve su recibo original sin nuevos movimientos; otro intento devuelve 409. Conservar `budget_plan`, sus recibos y `transfer_request` al revertir imágenes. No restaurar un respaldo sobre movimientos posteriores como consecuencia implícita de una reversión visual.

## Contrato HTTP

Base `/api/budget-plans`. `userId` sigue el contrato existente declarado por el cliente; **no agrega autenticación**. La web actual declara usuario 1. La comprobación de pertenencia limita referencias respecto de ese usuario declarado; no protege frente a alguien que suplante otro `userId`. La autenticación del producto requiere un trabajo separado antes de exponerlo a usuarios no confiables.

| Método y ruta                   | Entrada / efecto                                                                                                                          |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| GET `/`                         | `userId`, `page`, `pageSize`; listado paginado, sin escrituras.                                                                           |
| GET `/options`                  | `userId`; cuentas y sobres activos USD/CRC del usuario, saldos agregados en una consulta de sobres.                                       |
| GET `/:id`                      | `userId`; documento, revisión, cálculo y recibo persistido.                                                                               |
| PUT `/:id`                      | `{userId,expectedRevision,document}`; crear con revisión 0 o guardar borrador. Hash del cuerpo/revisión hace repetible el mismo guardado. |
| POST `/:id/finalize`            | `{userId,revision}`; validar y preparar; sin movimientos.                                                                                 |
| POST `/:id/reopen`              | `{userId,revision}`; volver a borrador antes de asignar.                                                                                  |
| POST `/:id/delete`              | `{userId,revision}`; eliminar solo borrador actual. Reservado al contrato API; la UI nueva no ofrece borrado del plan completo.           |
| GET `/:id/previous-assignments` | `userId`; propuesta de líneas/fuentes anteriores, sin guardar.                                                                            |
| GET `/:id/funding-preview`      | `userId`; destinos, fuentes, importes y disponibilidad actual.                                                                            |
| POST `/:id/fund`                | `{userId,revision,requestId,date}`; aplicar todo o nada, devolver recibo con IDs de movimientos.                                          |

Validación estricta con Zod, consultas parametrizadas, UUID y fechas válidas, máximos de 200 líneas/100 fuentes, importes acotados y precisión de entrada explícita. Error `FEATURE_NOT_READY` 503 si `budget_plan` falta o no coincide con la definición exacta; el arranque no la crea. Fondear además necesita la tabla de idempotencia de ZA-90. Errores inesperados no publican SQL/rutas internas. El recibo no contiene credenciales ni datos bancarios externos.

## Preparación y pruebas

El instalador compilado `node dist/scripts/enable-budget-plans.js --db <archivo existente de testing>` es aditivo, explícito y repetible; exige archivo existente, conserva tablas históricas y rechaza una definición incompatible o triggers inesperados. No ejecutar sobre la copia productiva de auditoría. El helper SSH instalado en el Mac el 4 de noviembre **solo conoce ZA-90**: necesita una ampliación local revisada y nuevos pins antes de automatizar esta preparación; ver la guía de despliegue. Esta implementación no cambia ese endpoint remoto.

`tests/budget-plan.test.ts` usa una DB temporal sintética y HTTP real. Comprueba cálculo, redondeo individual, entradas vacías, esquema repetible/incompatible, revisiones, pertenencia, cuerpos estrictos, preparación, aplicación USD/CRC balanceada, reintento, rollback completo, saldo insuficiente, fechas y copia/borrado. `npm test` también ejecuta las suites históricas. Las pruebas web cubren el contrato de recibos, recuperación y lectura accesible. Ninguna prueba usa bases del usuario.
