# ZA-101 · Medición temporal de SQLite y API

La captura está apagada por defecto. Para una ventana de diagnóstico, iniciar la API con ZANDAKA_PERF_ENABLED=true y ZANDAKA_PERF_SAMPLE_RATE entre 0 y 1 (predeterminado 0.1). Una tasa 0 conserva conteos sin tiempos. Una tasa inválida desactiva la captura. Retirar la variable o ponerla en false y reiniciar para apagarla.

Cada minuto el proceso emite una línea JSON cuyo evento es zandaka_performance en stdout. Consultar el registro existente del contenedor o proceso y seleccionar las ventanas UTC mediante from y to. Cada ventana presenta ranking por ejecución/solicitud, con kind sql o http, y tableRanking con las lecturas y escrituras en las que aparece cada tabla conocida. Una consulta puede contar para varias tablas. Para investigar latencia, ordenar las filas por meanMs o p95UpperMs dentro del mismo tipo y considerar el número de muestras. El ID SQL es una huella de la plantilla normalizada, la operación y la versión del código determinan su interpretación. No es un identificador de usuario. Las rutas HTTP son las plantillas registradas por Express, sin parámetros resueltos ni query strings.

El conteo no se muestrea. El tiempo se selecciona aleatoriamente por operación, con media y percentiles aproximados por límite superior de intervalos. p50 exige al menos 20 muestras y p95 exige 100. Los valores null indican cobertura insuficiente y >5000 indica el último intervalo abierto, en milisegundos. totalSampleMs es el tiempo de la muestra, no el tiempo acumulado real. No promediar percentiles entre ventanas. Los tiempos se asignan al cierre de la operación, incluyen fallos de ejecución SQL y respuestas HTTP terminadas de rutas registradas. SQL mide get/all/run de sentencias preparadas después de inicializar la conexión, sin incluir preparación, exec, iteradores, comprobaciones de arranque ni consultas de otros procesos. HTTP mide desde el router hasta finish, sin incluir lectura del cuerpo previa al router, solicitudes abortadas ni rutas sin coincidencia. El catálogo de tablas se obtiene de referencias explícitas en plantillas conocidas, sin expandir vistas, triggers ni el plan de SQLite. Los conteos SQL no representan visitas web.

Por proceso y ventana se conservan hasta 512 series con histogramas fijos. dropped cuenta observaciones descartadas al superar el límite. La memoria se vacía tras emitir el resumen y las ventanas incompletas se pierden al terminar el proceso. Para el diagnóstico conservar como máximo siete días en el registro con rotación del entorno. La aplicación no agrega archivos, tablas ni endpoints y no controla la retención de Docker. Solo se emiten agregados, huellas SQL y etiquetas conocidas, sin texto SQL, parámetros, resultados, cuerpos, URLs reales o identificadores personales.

Prueba sintética local con SQLite en memoria. Una lectura indexada por clave primaria promedió por operación, según la mediana de ocho rondas de 20 000 prepare+get y calentamiento, 3.8 µs sin captura y 9.2 µs con captura al 10 % (unos 5.4 µs adicionales). Este microbenchmark de consultas diminutas incluye normalizar cada prepare y no mide latencia HTTP ni impacto en el Mac. El recorrido de aceptación ordenó 120 lecturas rápidas antes de 20 escrituras sintéticas con dos milisegundos de espera, distinguió sus tiempos y omitió el p95 de las escrituras por falta de muestras. Ejecutar node --test -r ts-node/register tests/performance.test.ts para reproducir la aceptación.

El ranking de uso real aún requiere una ventana habilitada y observada en el entorno elegido. ZA-101 no requiere preparar DB ni cambiar índices. El despliegue habitual puede conservar la captura apagada.
